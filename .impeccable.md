# Impeccable — project design context

## Design Context

### Users
A single developer (the repo owner), operating the app on `localhost` from a desktop browser or the
`--native` desktop window. No second audience: nobody else ever sees this UI, and it is never opened
on a phone or tablet. The user already knows every `main-yt-dlp.py` flag by heart — the form is a
faster way to assemble a command they could type, not a way to avoid learning it.

The job to be done: pick a preset, paste or confirm a URL, launch, and then **read the streaming
subprocess output** until the run ends. The output log is the primary surface; the form is the
staging area you leave behind once Launch is pressed.

### Brand Personality
Utilitarian, dense, fast — an instrument panel. Terminal-adjacent. It should feel like a control
surface for a machine already understood, not a product being sold. No decoration, no onboarding, no
reassurance copy. Legibility and information density beat comfort and whitespace.

### Aesthetic Direction
Dark, derived from context rather than fashion: a desk tool run alongside a terminal, often at night,
whose main content is ANSI-coloured subprocess output that was authored for a dark terminal
background. Monospace for output, proportional for chrome.

Anti-references: consumer media-downloader web UIs, marketing-page aesthetics, anything that would
look at home with a hero section.

### Design Principles
1. **The log is the product.** Vertical space, contrast, and colour fidelity in the output log
   outrank every form-level nicety.
2. **Hierarchy by weight, not by hue.** One action is pressed every session (Launch); the rest are
   rare or destructive. Colour is not a substitute for rank.
3. **Colour must survive the theme.** Any colour that cannot be read on the configured background is
   a bug, not a style preference — this includes the ANSI palette.
4. **Event, not poll.** State updates ride on the change that caused them; nothing idles in a loop.
5. **Pragmatic accessibility.** Contrast, keyboard reach, and focus are in scope because they affect
   the one real user. Formal ARIA/screen-reader conformance is not a goal for this surface.

### Accessibility bar
Pragmatic, not WCAG-conformance-driven. Report contrast, keyboard, and focus defects that would
actually bite a sighted desktop user; do not file ARIA/landmark/screen-reader findings.

### Viewports
Desktop only. Mobile and tablet breakage is out of scope and must not be scored. Desktop *window*
behaviour (short windows, tall monitors, narrow resizes) is in scope.
